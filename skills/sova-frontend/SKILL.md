# SOVA Frontend Guidelines

Ты работаешь над существующим frontend-проектом SOVA — сайтом феминистского онлайн-журнала.

Твоя задача — помогать развивать и поддерживать проект, сохраняя существующую архитектуру и стиль кода. Перед внесением изменений сначала изучай релевантную структуру проекта и существующие компоненты. Не переписывай архитектуру без необходимости.

## Общие правила работы

1. Всегда сначала анализируй существующий код и архитектуру проекта.
2. Не создавай новые абстракции или компоненты, если аналогичная логика уже существует.
3. Перед изменением компонента ищи похожие компоненты и следуй уже используемым в проекте паттернам.
4. Не меняй рабочую архитектуру проекта только ради того, чтобы применить другой подход.
5. Если есть несколько разумных вариантов реализации, сначала кратко объясни различия и предложи наиболее подходящий для текущего проекта.
6. Не удаляй существующий код или файлы без явной необходимости. Если считаешь, что файл больше не нужен, сначала объясни почему.
7. Не добавляй комментарии `TODO` в код. Если появляются задачи, которые нужно сделать позже, сообщай о них отдельно.
8. Не изменяй несвязанные с текущей задачей части проекта.
9. После изменений проверяй TypeScript-ошибки, импорты, пути к файлам и очевидные ошибки сборки.
10. Если изменение затрагивает несколько файлов, сначала покажи предполагаемую структуру изменений, а затем реализуй её.
11. Не придумывай API, компоненты или файлы, которых нет в проекте, если для этого нет необходимости.
12. Сохраняй существующий стиль форматирования, именования и организации файлов.

## Технологический стек

Проект использует:

* React
* TypeScript
* Vite
* React Router
* CSS Modules

Основные сущности проекта:

* `src/pages` — страницы приложения
* `src/components` — переиспользуемые UI-компоненты
* `src/data` — данные и контент
* `src/assets` — изображения и другие статические ресурсы
* `src/types` — общие TypeScript-типы
* `src/router.tsx` — конфигурация маршрутизации, если используется текущая архитектура с `createBrowserRouter`

## Архитектурные принципы

### Страницы

Страницы находятся в `src/pages`.

Страница должна отвечать преимущественно за композицию компонентов и получение необходимых данных.

Не следует помещать в страницу большую HTML-разметку, если эту разметку можно вынести в отдельный переиспользуемый компонент.

### Компоненты

Переиспользуемые элементы находятся в `src/components`.

Если компонент имеет собственную сложную логику или стили, предпочтительно использовать отдельную папку:

```text
ComponentName/
├── ComponentName.tsx
└── ComponentName.module.css
```

Не создавай компонент только ради искусственного разделения кода. Если блок используется один раз и не имеет собственной логики, сначала оцени, действительно ли его нужно выносить.

### Данные

Контент сайта должен быть отделен от компонентов отображения.

Например, статьи хранятся отдельно от `ArticleContent`:

```text
src/
├── data/
│   └── articles/
│       ├── index.ts
│       ├── news-1.ts
│       ├── news-2.ts
│       └── news-3.ts
├── types/
│   └── article.ts
```

Компоненты должны получать данные через props и отвечать за отображение.

### Статьи

Статья представляет собой структурированные данные.

Примерно:

```ts
type ArticleArgs = {
  slug: string;
  tag: string;
  title: string;
  date: string;
  readingTime: string;
  content: ArticleContent[];
};
```

Контент статьи состоит из типизированных блоков, например:

* `paragraph`
* `heading`
* `image`
* `banner`
* `related`

Для контента используется discriminated union по полю `type`.

`ArticleContent` отвечает за отображение массива контентных блоков и не должен содержать данные конкретной статьи.

Статьи собираются в единый объект/реестр по `slug`, чтобы их можно было получать динамически.

Например:

```ts
export const articles = {
  [news1.slug]: news1,
  [news2.slug]: news2,
  [news3.slug]: news3,
};
```

При работе со страницей статьи необходимо использовать `slug` из React Router и получать соответствующую статью из реестра.

Если статья не найдена, необходимо предусмотреть корректное поведение, а не обращаться к `undefined`.

### Маршрутизация

Если в проекте используется:

```ts
createBrowserRouter()
```

и:

```tsx
<RouterProvider />
```

то `router.tsx` является единым источником истины для маршрутов.

Не создавай параллельную систему маршрутизации через `<BrowserRouter>`, `<Routes>` и `<Route>`, если текущая архитектура уже построена на data router.

При добавлении новых страниц добавляй соответствующий маршрут в существующий `router.tsx`.

### Изображения

Изображения, являющиеся частью контента статьи, должны храниться в `src/assets` и импортироваться в data-файлах, если это соответствует текущей структуре проекта.

Не дублируй импорт изображений в компонентах отображения.

Компонент должен получать готовый `src` через данные.

Всегда проверяй правильность относительного пути импорта относительно конкретного файла.

## Работа с задачами

Когда я ставлю новую задачу:

1. Сначала определи, какие существующие файлы и компоненты затрагиваются.
2. Проверь, есть ли уже подходящий компонент или паттерн.
3. Определи минимальный набор изменений.
4. Если архитектурное решение неоднозначно — предложи варианты до реализации.
5. После моего подтверждения внеси изменения.
6. В конце кратко перечисли:

   * какие файлы изменены;
   * что именно сделано;
   * какие потенциальные проблемы или следующие шаги остались.

Если задача простая и решение очевидно, не задавай лишних вопросов и сразу реализуй её.

## Важный принцип

Главная цель — не просто сделать текущую задачу рабочей, а постепенно построить поддерживаемую архитектуру проекта.

При этом не нужно преждевременно усложнять проект. Предпочтение отдавай простому решению, которое соответствует текущему масштабу приложения и может быть безболезненно расширено позже.

Если видишь архитектурный долг или потенциальную проблему, не исправляй её автоматически, если она не относится к текущей задаче. Сначала сообщи о проблеме и предложи решение.

Перед каждым существенным рефакторингом объясняй:

* какую проблему он решает;
* почему текущий подход недостаточен;
* что изменится в структуре проекта;
* какие будут плюсы и минусы.
